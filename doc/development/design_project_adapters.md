# Staged project settings adapter

The design-backed Settings adapter is implemented but **not integrated into the production General Settings route**. `app/views/projects/edit.html.haml` and `pages/projects/edit/index.js` retain their original content and initialization. The staged `mountProjectSettings` entrypoint is not called by that route. Activation is blocked until the replacement implements the working settings operations enumerated below. No duplicate original panel is embedded in the design surface, and no hidden alternate route was created.

`createProjectSettingsAdapter` reads project metadata through GraphQL, selecting only ID, name, visibility, and avatar URL. It deliberately avoids the project REST entity, which can include runner registration credentials for authorized administrators. Name, numeric visibility, and multipart avatar updates use the existing Rails project update action with JSON response format. The shared update-result handler returns only name, visibility, and avatar URL on success or a bounded generic validation error on failure. Its existing authorization, CSRF, and step-up checks are preserved. REST v4 handles direct project members and protected branches. Role updates send numeric `access_level`; removing a member affects direct membership only. Protected branches are addressed by their encoded names. Collections follow pagination up to 100 pages and fail explicitly rather than silently dropping additional records.

CI/CD variable listing uses the existing GraphQL `project.ciVariables` field and requests metadata only. The query does not select `value`. Environment scope accompanies each variable, and every single-variable operation encodes both the key and its exact scope. Generic reveal is disabled in the production adapter and never fetches, caches, or renders a stored variable value. The staged surface links to the existing dedicated CI/CD variables editor for value inspection. Hidden variables remain unrevealable. Creating a variable takes user-entered fields and clears the local form on submission or cancellation. Metadata refresh never retains values, and failed mutations never reflect server response bodies into notifications because they can echo submitted credentials.

Integration listing requests only `IntegrationBasic`, which contains no provider credentials. The production surface lists active integrations and links to the existing configuration editor. It does not use the REST deletion operation as a toggle: that implementation resets configuration fields. Enabling arbitrary integrations also requires provider-specific inputs. The adapter therefore rejects generic toggle methods with an explicit instruction to use the dedicated editor. Logo color presets are omitted in production because project metadata has no persisted logo-color setting; an uploaded project avatar is shown using the actual server URL.

## Explicit capability gaps

The staged General tab does not yet represent description, topics, badges, project feature permissions, Duo settings, issue templates, service desk, housekeeping, object pruning, export, archive, path changes, transfer, fork unlinking, restore, deletion, or enterprise policy settings. All existing controls continue to work in the unchanged production General Settings route. The replacement must expose equivalent authorized controls before activation. Integration configuration uses its existing dedicated route. Direct-member management does not list or modify inherited memberships, invitations, or access requests. These limitations block activation and are not completed design parity.

Requests preserve session authentication and CSRF headers, reject non-local endpoints and redirects, and leave server-side authorization intact. Independent read failures are reported separately. Mutations publish server-refreshed state, and a partially accepted bulk operation reloads state before showing its failure. Concurrent UI mutations are serialized by disabling or rejecting a second pending operation.

Focused behavioral coverage is in `spec/frontend/material_system/settings_project_adapter_spec.js` and `project_surfaces_interaction_spec.js`. It covers actual REST/GraphQL response shapes, pagination, metadata privacy, scoped variable deletion, disabled generic reveal, hidden-variable refusal, numeric roles, avatar multipart upload, mutation error privacy, and unsupported integration operations. Runtime and rendered evidence must be obtained after equivalent controls exist and the production route is explicitly activated. Adapter tests alone do not establish production integration.
