# Project settings production adapter

The project General Settings route (`/:namespace/:project/edit`) mounts the design-backed Settings surface through `pages/projects/edit/index.js`. The Rails view supplies project identity, relative installation prefix, and permission flags evaluated with the existing project abilities. Project administrators receive the replacement surface, not a duplicate of the original settings panel. Existing limited nonadministrator views remain subject to their original permissions. No authorization controller or route is replaced.

`createProjectSettingsAdapter` reads project metadata through GraphQL, selecting only ID, name, visibility, and avatar URL. It deliberately avoids the project REST entity, which can include runner registration credentials for authorized administrators. Name, numeric visibility, and multipart avatar updates use the existing Rails project update action with JSON response format. The shared update-result handler returns only name, visibility, and avatar URL on success or a bounded generic validation error on failure. Its existing authorization, CSRF, and step-up checks are preserved. REST v4 handles direct project members and protected branches. Role updates send numeric `access_level`; removing a member affects direct membership only. Protected branches are addressed by their encoded names. Collections follow pagination up to 100 pages and fail explicitly rather than silently dropping additional records.

CI/CD variable listing uses the existing GraphQL `project.ciVariables` field and requests metadata only. The query does not select `value`. Environment scope accompanies each variable, and every single-variable operation encodes both the key and its exact scope. Revealing a non-hidden variable requires its explicit row action and retrieves only that variable; hiding it discards the rendered value without another request. Hidden variables cannot be revealed. Creating a variable takes user-entered fields and clears the local form on submission or cancellation. Metadata refresh never retains values, and failed mutations never reflect server response bodies into notifications because they can echo submitted credentials.

Integration listing requests only `IntegrationBasic`, which contains no provider credentials. The production surface lists active integrations and links to the existing configuration editor. It does not use the REST deletion operation as a toggle: that implementation resets configuration fields. Enabling arbitrary integrations also requires provider-specific inputs. The adapter therefore rejects generic toggle methods with an explicit instruction to use the dedicated editor. Logo color presets are omitted in production because project metadata has no persisted logo-color setting; an uploaded project avatar is shown using the actual server URL.

## Explicit capability gaps

The replacement General tab does not yet represent description, topics, badges, project feature permissions, service desk, transfer, archive, deletion, object pruning, export, fork unlinking, or enterprise policy settings. The initial General view names its limitation rather than claiming full settings parity. The backend operations remain intact, but a complete general-settings migration must expose these controls before that surface can be marked complete. Integration configuration uses its existing dedicated route. Direct-member management does not list or modify inherited memberships, invitations, or access requests. These limitations are not evidence of completed design parity.

Requests preserve session authentication and CSRF headers, reject non-local endpoints and redirects, and leave server-side authorization intact. Independent read failures are reported separately. Mutations publish server-refreshed state, and a partially accepted bulk operation reloads state before showing its failure. Concurrent UI mutations are serialized by disabling or rejecting a second pending operation.

Focused behavioral coverage is in `spec/frontend/material_system/settings_project_adapter_spec.js`. It covers actual REST/GraphQL response shapes, pagination, metadata privacy, scoped variable operations, hidden-variable refusal, numeric roles, avatar multipart upload, mutation error privacy, and unsupported integration operations. Runtime and rendered evidence must be obtained from the built project route before claiming full production verification.
